ECC UX/UI 팀 9주차 스터디. 범위는 두 권에 걸쳐 있다. 『UX·UI 디자인 교과서』 3부 4장 '워크플로와 정보 구조'(328~342쪽)와 『실전 피그마』 PART 5 '컴포넌트 & 배리언츠 적용하기'(146~213쪽)다. 11월 9일에 대면으로 모였고 14일까지가 9주차 기간이었다.

## 3부 4장. 워크플로와 정보 구조

4장은 시스템의 각 사용 단계를 나타내는 워크플로, 시스템 설계의 전체 그림과 흐름을 결정하는 설계도 역할의 정보 구조, 이것들을 토대로 하는 메뉴 설계, 메뉴 구조에 필요한 카드소팅을 차례로 다룬다.

### 인터랙티브 시스템의 구성 요소

인터랙티브 시스템은 사용자와 시스템의 상호작용 방식을 정의하는 다양한 요소로 구성된다. 수많은 앱이 들어 있는 스마트폰부터 웹사이트, 애플리케이션, 리모컨이나 컨트롤 패널로 조작하는 전자제품, VR, AR, 메타버스가 모두 포함된다. 이것들을 사용할 때 시스템과 상호작용이 생기므로 인터랙티브 시스템이라고 한다.

![인터랙티브 시스템의 구성 요소]({{ '/assets/images/club-ecc-ux-ui/ia-interactive-system.svg' | relative_url }})

| 구성 요소 | 뜻 | 교재 예 |
| --- | --- | --- |
| 시스템 | 하나의 인터랙티브 시스템. 여러 서비스로 구성된다 | 스마트폰, 세탁기, 박물관 웹사이트 |
| 서비스(=기능) | 시스템 안의 각 기능 | 스마트폰의 통화·카메라·SNS·지도 앱, 세탁기의 세탁·건조, 박물관 웹사이트의 박물관 소개·전시 안내·회원 관리 |
| 메뉴 구조 | 각 기능에 접근할 수 있게 해 주는 구조 | 피처폰 메뉴, 전자제품과 리모컨, 웹사이트 메뉴 |
| 워크플로 | 어떤 목적을 수행하기 위해 정보 구조 안에서 거쳐 가는 경로 | 전시 예매: 예매 전시 확인 → 결제 수단 선택 → 결제 진행 → 결제 결과 확인 |
| 스크린 | 시스템의 화면(스크린숏). 인터랙션 행위의 말단 | 카메라 앱도 꽤 많은 스크린숏으로 구성된다 |

그림은 교재 그림 3.23을 다시 그린 것이다. 바깥의 큰 상자가 시스템, 그 안의 세 상자가 서비스, 작은 사각형들이 스크린이다. 서비스는 기능이라고 생각해도 된다. 스마트폰이라면 앱 하나하나가 서비스다. 박물관 웹사이트의 '전시 안내'는 상설전과 특별전으로 나뉘고 전시 작품 소개, 예매 정보 안내, 결제 같은 구체적인 단계로 구성되므로, 서비스는 하위 단계에 비해 추상적인 개념이고 여러 서비스의 복합체인 시스템은 더 추상적인 개념이다.

사용자는 서비스라는 추상적인 개념이 아니라 화면이나 소리 같은 감각을 통해 서비스를 경험한다. 경고음이나 음성 가이드도 중요하지만 대부분의 인터랙션은 화면을 통해 이루어진다. 그래서 스크린숏은 가장 직접적이고 비중이 높은 인터랙션 행위의 말단이자 사용자 인터페이스의 핵심적인 구성 요소다. 스크린숏은 '페이지'라는 용어로 대체할 수 있다.

정보 구조는 하나의 시스템 안에 들어 있는 서비스 또는 기능을 조직화하고 구조화한 것이다. '구조'는 관련이 깊은 것들을 체계적으로 모아 놓았다는 뜻이다. 박물관 웹사이트에 SNS에나 있을 법한 친구 찾기 서비스는 들어 있지 않고, '회원 관리' 안에 회원 가입과 내 정보 보기 및 변경이 모여 있다. 기능과 서비스를 굳이 '정보'라고 부르는 이유도 교재에 나온다. 대부분의 인터랙티브 시스템이 인지적인 정보를 중심으로 만들어져 왔기 때문에 UI 디자인과 HCI 분야에서 그렇게 불러 왔다.

| 구분 | 구조 | 역할 |
| --- | --- | --- |
| 정적 | 정보 구조 | 조직화되어 있는 시스템의 서비스·기능 |
| 동적 | 메뉴 구조 | 각 기능에 접근하게 해 준다. 일반적으로 트리 구조라고도 하는 계층 구조 |
| 동적 | 워크플로 | 목적을 수행하기 위해 정보 구조 안에서 거쳐 가는 경로 |

조직화되어 있는 정보 구조를 사용자가 쓰려면 메뉴 구조나 워크플로 같은 동적인 구조가 필요하다. 그림에서 위쪽 점에서 각 서비스로 뻗는 선이 메뉴 구조이고, 가운데 서비스 안에서 화면을 따라 내려가는 파란 선이 워크플로다. 메뉴 구조의 예로 교재는 피처폰을 든다. 스마트폰에서는 필요성이 없어졌지만 피처폰에는 수많은 기능을 묶어 주는 메뉴 구조와, 상하좌우 방향키·OK 키·취소키로 된 내비게이션 키 세트가 있었다. 이 조합은 여전히 여러 전자제품과 리모컨에 들어 있다.

### 워크플로

> 한 개의 태스크를 나타내는 순차적인 조작 절차를 워크플로라고 한다.

워크플로는 특정 목표를 달성하기 위해 업무나 작업이 어떻게 흐르는지를 정의한 것이고, 작업의 단계별 순서, 각 단계에서 수행해야 할 작업, 시스템 간의 상호작용을 포함한다. 소프트웨어나 하드웨어의 사용 절차뿐 아니라 비즈니스 프로세스, 프로젝트 관리, 시스템 설계에도 쓰인다. 교재는 제품을 샀을 때 들어 있는 매뉴얼을 떠올리면 이해하기 쉽다고 한다. 프린터의 '처음 시작하기' 안내서가 설치 과정을 순서대로 보여 주는 것이 워크플로의 일종이다.

사례는 이번에도 쏘카다. 1~4주차에 인터뷰, 동행 관찰, 퍼소나, 여정 지도에서 계속 나왔던 그 프로젝트다. 그림 3.24는 KTX로 다른 도시에 도착한 뒤 쏘카를 쓰는 '쏘카와 KTX' 서비스의 예약 과정을 화면으로 이은 것이다.

| 구간 | 화면 |
| --- | --- |
| 이동 홈 | 홈 탐색 |
| KTX 예약 | 주차 안내 확인 → 출발·도착역 선택 → 날짜 선택 → 인원 선택 → 가는 날 탑승 시간·좌석 선택 → 오는 날 탑승 시간·좌석 선택 → 선택 열차 정보 확인 |
| 차량 예약 | 역 근처 예약 장소 탐색 → 차량 탐색 또는 예약 장소 확인 → 예약 정보 확인 → 주차 장소 구체화 또는 사고부담금 선택 (두 갈래) |
| 결제하기 | 요금 확인 및 할인 적용 |

특정 태스크 하나만 보여 주기 때문에 각 화면이 순차적으로 연결되어 복잡해 보이지 않는다. 그러나 모든 태스크를 다 연결하면 표현하기 어려울 정도의 화살표와 스크린숏이 그려진다. 하나의 화면은 하나의 경로로만 연결되지 않기 때문이다. '결제하기' 화면은 '쏘카와 KTX' 메뉴를 통해서도 들어가지만 홈 화면의 '가지러 가기'나 '여기로 부르기'를 통해서도 들어간다.

워크플로는 추상성의 정도에 따라 나눌 수 있다.

| 수준 | 표현 | 교재 그림의 달력 예 |
| --- | --- | --- |
| 가장 추상적 | 단어 | 'Calendar Month view'라는 글자 |
| 중간 | 와이어프레임 스케치 | 'MM YYYY' 머리와 빈 격자 |
| 가장 구체적 | 스크린숏 | 'JANUARY 2020' 실제 달력 화면 |

추상성이 높은 워크플로는 각 단계를 단순한 텍스트, 도형, 연결선만으로 나타내고, 추상성이 낮은 워크플로는 스크린숏에 가깝다. 어느 쪽이 더 낫다는 것이 아니라 상황에 따라 맞는 수준이 다르다.

### 유저플로와 해피 패스

두 개념은 모두 사용자 입장에서 바라본 워크플로다.

| 구분 | 유저플로(User Flow) | 해피 패스(Happy Path) |
| --- | --- | --- |
| 정의 | 사용자가 제품이나 서비스를 사용하면서 겪는 다양한 경로와 상호작용을 시각적으로 표현한 것 | 오류나 예외 상황 없이 목표를 성공적으로 달성하는 이상적인 경로 |
| 범위 | 사용자가 겪을 수 있는 모든 경로 | 그중 최적의 경험을 제공하는 하나의 경로 |
| 중점 | 전체 사용자 경험을 시각화한다 | 이상적인 사용자 경험을 보장한다 |
| 용도 | 시스템 설계와 문제 해결에 도움을 준다 | 시스템이 최상의 경험을 제공하는지 확인한다 |
| 교재 예 | 온라인 쇼핑몰에서 회원 가입 → 상품 검색 → 장바구니 → 결제 완료 | 올바른 아이디와 비밀번호를 입력해 로그인에 성공하는 과정 |

유저플로는 시작, 단계, 의사 결정 지점, 경로, 종료 다섯 요소로 이루어진다. 해피 패스의 특징은 예외 상황 없음, 최적의 경험, 효율성 세 가지이고, 시스템의 성공적인 동작을 보장하기 위해 설계 단계에서 우선적으로 고려된다.

### 정보 구조의 유형

정보 구조(IA, Information Architecture)는 사용자가 시스템, 소프트웨어, 웹사이트, 애플리케이션을 탐색할 때 정보를 어떻게 배치하고 조직할지를 정의한다. 형태가 다양하고 구조마다 장단점이 있어서, 이를 파악하고 선택·설계할 수 있어야 한다.

![정보 구조의 유형]({{ '/assets/images/club-ecc-ux-ui/ia-structure-types.svg' | relative_url }})

| 유형 | 형태와 특징 | 교재 예 |
| --- | --- | --- |
| 선형 | 정보가 순차적으로 배열된다. 시작·다음·종료로 정의되는 가장 간단한 구조이고 구축하기도 쉽고 저렴하다 | 책 읽기, ATM 인출 화면, 문자메시지 전송, 인터넷 쇼핑 결제, 설치 마법사 |
| 그리드형 | 정보를 2차원 이상으로 배열한다. 직관적으로 찾을 수 있고 비교가 쉽다. 매트릭스라고도 부른다 | 스마트폰 홈스크린, 데이터베이스 시스템, 테이블 |
| 계층(트리)형 | 계층적 질서로 배치된다. 상위 구조가 여러 하위 항목을 포함한다. 그룹핑이 되고 단축키를 할당할 수도 있다 | 일반적인 메뉴 구조, 조직도, 가계도 |
| 그물형 | 정보 간의 링크가 무제한적이고 직접적으로 연결된다. 한쪽이 연결되지 않아도 다른 쪽으로 우회할 수 있다 | 페이스북, 인스타그램 같은 SNS |
| 링형 | 정보가 순환형으로 배열된다. 시작 지점으로 돌아오도록 유도할 때 유용하다. 반대편으로 이동할 때 시간이 걸린다 | 미술관의 동선, 이케아 매장의 전시관, 서울 지하철 2호선 |
| 스타형 | 중심 노드에서 여러 정보가 방사형으로 뻗어 나간다. 중심을 허브라고도 부른다 | 허브 공항, 대형 쇼핑몰, 포털사이트와 검색엔진 |
| 하이브리드형 | 여러 유형을 결합한다. 대부분의 네트워크는 하이브리드 구조다 | 대학이나 기업의 네트워크, 대형 전자상거래 사이트 |

그림에는 교재 그림 3.26과 같이 여섯 유형만 그렸고, 하이브리드형은 본문에만 나온다. 앞 절의 워크플로는 이 표의 선형 구조에 해당한다. 하나의 목적을 위해 시작 페이지부터 끝까지 순차적으로 밟아 나가기 때문이다.

쏘카의 '이동' 정보 구조(그림 3.27)가 하이브리드의 예다. Depth 1의 '쏘카/이동' 아래에 Depth 2로 가지러 가기, 여기로 부르기, 편도로 타기, 쏘카와 KTX, 전기 자전거, 쏘카 플랜, 마이페이지, 알림 센터가 놓이는 전형적인 계층 구조다. 그런데 여러 메뉴의 경로가 마지막에는 예약/결제 → 반납하기 → 추가 요금 결제라는 같은 줄로 모인다. 예약과 결제, 반납 절차에서는 선형 구조를 채택한 것이다.

### 정보 구조 선택 시 고려 사항

| # | 고려 사항 | 내용 |
| --- | --- | --- |
| 1 | 사용자의 요구 | 사용자가 정보를 어떻게 탐색할지를 고려해 가장 직관적인 구조를 고른다. 전자상거래 웹사이트의 제품 카테고리는 논리적이고 사용자의 심성 모형에 가까워야 한다 |
| 2 | 정보의 유형 | 정보가 얼마나 복잡하고 서로 연관되어 있는지를 본다. 복잡한 데이터베이스는 계층 구조나 네트워크 구조가 필요하지만, 정보가 단순하면 복잡한 분류가 오히려 탐색에 지장을 준다 |
| 3 | 유연성과 확장성 | 새 콘텐츠나 기능이 추가될 때 기존 구조를 크게 바꾸지 않고 통합될 수 있어야 한다. 유연성이 없는 구조는 장기적으로 유지 관리가 어렵다 |
| 4 | 효율성 | 최소한의 클릭이나 탐색으로 목표에 도달하게 한다. 모바일 디바이스는 화면 크기의 제한 때문에 효율성이 더 중요하다 |

여기에 교재는 스마트폰 이후의 변화를 덧붙인다. 피처폰 시절에는 정보 구조가 고정된 메뉴 구조에 의해 엄격하게 규정되었고 사용자는 설계된 구조를 따라야 했다. 스마트폰에서는 사용자가 앱 아이콘과 위젯 배열을 사용 빈도, 카테고리, 공간 메타포에 따라 자유롭게 구성한다. 자주 쓰는 앱을 손이 닿기 쉬운 자리에 두고, 카테고리별로 묶거나 폴더로 정리한다.

> 스마트폰의 등장으로 정보 구조 설계의 사용자 통제권이 급격히 확대되었다.

정보 구조는 고정된 틀이 아니라 개인의 필요에 따라 바뀌는 유동적인 형태가 되었고, 이 경향은 TV 같은 다른 전자제품으로도 퍼지고 있다. 채널과 볼륨만 조작하던 TV가 많은 정보를 보여 주는 플랫폼으로 바뀌면서 UI 구조도 크게 달라졌다.

| 6 | UI 디자인 | 폰트 스타일, 색상, 아이콘, 포커스 영역을 설계한다 |
| 7 | 프로토타이핑과 테스트 | 프로토타입을 만들어 실제 사용 환경에서 메뉴의 사용성을 테스트한다 |

그림은 교재 그림 3.28의 배치를 따랐다. 1~5단계가 UX 플래닝, 4~8단계가 UI 디자인 영역이어서 라벨링과 내비게이션 규칙 설정 두 단계는 양쪽에 걸친다. 1단계의 리서치 방법은 1~2주차에 읽은 인터뷰, 관찰, 설문 그대로다. 3단계에는 구체적인 지침이 하나 들어 있다.

> 대체적으로 넓고 얕은 구조가 좁고 깊은 구조보다 더 바람직하다.

교재 그림 3.28의 제목은 '사용자의 정보 구조 설계'로 붙어 있지만 내용은 메뉴 설계 단계다. 그림 속 첫 단계 이름도 본문의 '사용자 요구 분석'과 달리 '사용자 니즈 발굴'로 적혀 있다. 표와 그림은 본문 표기를 따랐다.

### 카드소팅

카드소팅(Card Sorting)은 메뉴 구조를 결정하는 주요 방법 중 하나다. 사용자가 정보를 어떻게 그룹화하고 구조화하는지를 이해하는 데 쓴다. 벽시계처럼 단순한 제품에는 메뉴가 필요 없지만, 복잡한 기능을 제공하는 디지털 제품에는 체계적인 메뉴 구성이 필수다.

| 구분 | 개방형 카드소팅 | 폐쇄형 카드소팅 |
| --- | --- | --- |
| 방법 | 사용자가 카드를 모은 뒤 상위 카테고리를 정한다 | 상위 카테고리를 미리 주고 하위 카드를 배치한다 |
| 쓰임 | 사용자 중심의 메뉴 구조 설계 | 구조화된 메뉴 설계 |
| 접근 | 상향식 | 하향식 |

수행 수단으로는 실제 카드와 테이블을 쓰는 수작업(오프라인)과 컴퓨터로 하는 소프트웨어(온라인) 방식이 있다. 소프트웨어 방식은 덴드로그램(Dendrogram)이나 유사도 매트릭스(Similarity Matrix) 같은 시각적 도구로 결과 분석을 돕는다. 장점은 사용자 중심 설계가 가능하다는 것, 효율성이 높다는 것, 개방형과 폐쇄형으로 유연하게 접근할 수 있다는 것, 분석 도구를 제공한다는 것 네 가지다.

상향식과 하향식은 1주차 인터뷰 정리에서 어피니티 다이어그램과 토픽별 정리로, 4주차 퍼소나 제작에서 다시 나왔던 구분이다. 메뉴 설계 3단계가 두 접근을 함께 쓰라고 한 것이 카드소팅에서는 개방형과 폐쇄형으로 나뉘어 있다.

### 1장. 컴포넌트로 동일한 형태를 반복해서 사용하기

버튼이나 아이콘처럼 같은 요소를 반복해서 쓰는 경우가 많다. 이전에는 반복 요소를 수정할 때 일일이 찾아 고쳐야 했다. 피그마에서 컴포넌트는 '디자인 전체에서 재사용할 수 있는 요소'로 정의되고, 핵심은 재사용성이다.

| 구분 | 메인 컴포넌트 | 인스턴스 컴포넌트 |
| --- | --- | --- |
| 만드는 법 | 오브젝트 선택 → Create component(`Ctrl+Alt+K`) | 메인 컴포넌트를 `Alt`+드래그로 복제 |
| 역할 | 인스턴스의 기본 속성을 정의한다 | 디자인에 직접 사용된다 |
| 관계 | 속성을 바꾸면 인스턴스도 함께 바뀐다 | 메인과 속성이 동기화되지만 독립적으로 바꿀 수도 있다 |
| Layer 패널 | 보라색 ❖ | 보라색 ◇ |

메인 컴포넌트는 디자인에 직접 쓰지 않고 별도 페이지에서 관리하는 것이 일반적이다. 교재의 Why?는 메인을 디자인에 직접 쓰면 메인과 인스턴스를 혼동해서 의도치 않게 모든 컴포넌트의 속성이 한 번에 바뀔 수 있다고 설명한다. 모든 컴포넌트는 자동으로 프레임화된다.

실습은 PART 4 3장의 버튼(W 120, FFE500, Stroke 000000 두께 2, Corner radius 8, 패딩 24/12)을 컴포넌트로 만드는 데서 시작한다. 메인의 색을 3E74FF로, 라벨을 '구매하기'로 바꾸면 인스턴스도 똑같이 바뀐다. 그다음이 이 장의 핵심이다.

| 메인에서 바꿨을 때 | 인스턴스에서 바꾼 적 있는 속성 | 인스턴스에서 바꾼 적 없는 속성 |
| --- | --- | --- |
| 결과 | 그대로 유지된다 | 메인을 따라 바뀐다 |
| 교재 예 | 색상, 라벨, 라벨 색 | 코너 둥글기, 텍스트 크기, 두께 |

![메인 컴포넌트와 인스턴스: 독립적으로 바꾼 속성은 유지된다]({{ '/assets/images/club-ecc-ux-ui/figma-p5-component-instance.png' | relative_url }})

위가 메인, 아래 셋이 인스턴스다. 가운데 인스턴스만 색을 FFE500으로, 라벨을 '글쓰기'로 바꿔 둔 상태에서 메인을 녹색 '확인'으로 바꾼 결과다. 양옆 인스턴스는 메인을 따라갔고 가운데 인스턴스는 색과 라벨을 지켰다. 인스턴스에서 독립적으로 변경된 속성은 메인의 영향을 받지 않는 상태가 된다. 그래도 가운데 인스턴스의 테두리와 코너 둥글기는 바꾼 적이 없으므로 메인에서 바꾸면 따라온다.

독립된 속성을 다루는 메뉴는 Component 패널의 'Instance options'(…)에 모여 있다.

| 메뉴 | 기능 |
| --- | --- |
| Reset all changes | 독립적으로 수정한 모든 변경값을 초기화한다 |
| Reset fill / Reset text | 개별 속성만 초기화한다 |
| Push changes to main component | 인스턴스의 독립 속성을 메인으로 이전한다. 메인과 모든 인스턴스가 그 속성으로 동기화된다 |
| Detach instance(`Ctrl+Alt+B`) | 인스턴스를 해제해 일반 프레임으로 되돌린다 |

초기화에 관한 Why?가 하나 있다. 색을 바꾼 인스턴스는 색을 메인과 다시 같게 맞춘다고 독립 속성이 풀리지 않는다. 'Reset fill'로 초기화해야 메인과 다시 동기화된다. Push changes가 필요한 이유도 앞의 관리 방식에서 나온다. 메인과 인스턴스를 다른 페이지에서 쓰는 경우가 많아서, 인스턴스로 시안을 잡다가 바꾼 속성을 메인에 적용하고 싶은 경우가 생긴다.

그 밖의 기능은 표로 모았다.

| 상황 | 방법 |
| --- | --- |
| 메인 컴포넌트 찾기 | 인스턴스 선택 → Component 패널의 'Go to main component'. 캔버스 아래 〈Return to instance〉로 돌아온다 |
| 메인이 삭제됨 | 인스턴스 선택 → Component 패널의 〈Restore Component〉. 복구된 메인은 기존 인스턴스와 자동 동기화된다 |
| 메인을 일반 프레임으로 | 메인은 Detach instance로 해제할 수 없다. 인스턴스를 복제해 해제한 다음 메인을 삭제한다 |
| 여러 개를 한 번에 컴포넌트로 | Create component 옆 확장 아이콘 → Create multiple components. 선택한 오브젝트가 각각 메인 컴포넌트가 된다 |

### 2장. 컴포넌트로 아이콘 관리하고 사용하기

아이콘은 프로젝트 전체에서 같은 형태를 반복해서 쓰는 컴포넌트 기능의 대표적인 예다.

| 단계 | 할 일 |
| --- | --- |
| 01~03 | 리소스 도구(`Shift+I`) → (Plugins) → 'icon' 검색 → Feather Icons에서 아이콘을 불러온다(홈, 피그마, 검색, 메뉴) |
| 04~07 | 불러온 아이콘은 레이어가 분리된 선 형태다. 프레임에서 `Enter`로 하위 레이어를 모두 선택 → Union selection → `Ctrl+E` → 레이어 이름 'icon' |
| 08 | 다른 아이콘도 같은 방법으로 통합하고 선을 면으로 바꾼다 |
| 09~10 | 아이콘 프레임을 모두 선택 → Create multiple components |
| 11 | 리소스 도구 → (Components) 탭에서 검색해 원하는 페이지에 불러온다 |

5주차 PART 3의 아이콘 실습에서 익힌 Union → Flatten → Outline stroke 순서가 그대로 쓰인다. Feather Icons는 사용자가 두께를 바꿀 수 있도록 Stroke 형태로 에셋을 제공한다. Figma 파일에서는 플러그인 에셋 대신 같은 모양을 직접 그린 뒤 Outline stroke, Union, Flatten으로 정리했다.

아이콘 묶음에 대해 교재가 권장하는 방식이 있다. 아이콘은 배리언츠를 쓰지 않고 각각의 컴포넌트 단위로 관리한다. 배리언츠로 묶으면 종류가 많을 때 밸류 목록에서 찾기 어렵고, 리소스 도구에서 원하는 아이콘을 바로 검색해 쓸 수 없기 때문이다.

모든 인스턴스 컴포넌트는 다른 인스턴스 컴포넌트로 스왑(Swap)할 수 있다. 인스턴스를 선택하고 Component 패널의 확장 아이콘에서 다른 컴포넌트를 고른다. 이때 목록이 정리되어 있어야 찾기 쉽다.

| 그룹화 방법 | 결과 |
| --- | --- |
| 메인 컴포넌트를 선택하고 `Ctrl+R` → Rename to에 'Icon/' 입력 → 〈Current name〉 → 〈Rename〉 | Icon/home, Icon/search처럼 바뀌고 Swap 목록에 'Icon' 폴더로 묶인다 |
| 아이콘 메인들을 프레임으로 감싸고 이름을 'General'로 | 'Icon' 위에 'General' 그룹이 하나 더 생긴다 |

레이어 이름에 '/'를 넣으면 그 앞이 폴더가 된다. '/'를 쓰지 않아도 파일 안의 위치에 따라 파일 → 페이지 → 섹션 또는 프레임 → 그룹 이름/컴포넌트 이름 순으로 자동 분류된다.

![아이콘 컴포넌트: General 프레임과 스왑한 인스턴스]({{ '/assets/images/club-ecc-ux-ui/figma-p5-icons.png' | relative_url }})

왼쪽 흰 프레임이 메인 컴포넌트 네 개를 감싼 'General'이고, 오른쪽 둘은 같은 인스턴스를 72×72로 키운 다음 home에서 search로 스왑한 것이다. 아이콘을 면으로 바꾸고 Constraints를 Scale로 둔 덕분에 3배로 키워도 선 굵기가 비율대로 따라 커졌다. PART 3에서 선 상태와 면 상태를 24~48px로 비교했던 내용이 여기서 컴포넌트 관리의 전제가 된다.

### 3장. 컴포넌트 프로퍼티를 활용한 체크리스트 만들기

컴포넌트 프로퍼티는 컴포넌트를 구성하는 요소들에 개별 속성을 부여해서, 디자인 과정에서 컴포넌트를 더 쉽게 쓰게 하는 기능이다.

재료는 두 가지다. 체크박스는 24×24 'square' 프레임 안에 16×16 'box'(Stroke DEDEDE, Corner radius 4)를 넣어 만들고, 복제한 'check-square'는 box를 6100FF로 채운 뒤 펜으로 체크 표시(FFFFFF, 두께 2, Round)를 그려 Outline stroke 한다. 둘을 Create multiple components로 컴포넌트로 만든다. 체크리스트는 '제목'(Medium 14)과 '상세 내용'(Regular 14, 777777)을 간격 4로 묶은 'text-label'에 square를 붙이고, 패딩 12, Fill FFFFFF, Stroke 000000, Corner radius 8, 너비 160으로 만든 'check-list'다. text-label과 그 안의 텍스트는 PART 4에서 배운 대로 모두 Fill container로 둔다.

여기에 프로퍼티 세 종류를 건다.

| 프로퍼티 | 설정 위치 | 대상 | 이름 | 인스턴스에서 |
| --- | --- | --- | --- | --- |
| 불리언(Boolean) | Layer 패널의 'Apply boolean property' | '상세 내용' 텍스트 | Show Detail (True) | 토글로 상세 내용을 보이거나 숨긴다 |
| 텍스트(Text) | Text 패널의 'Create text property' | '제목', '상세 내용' | Title, Detail | 텍스트를 직접 선택하지 않고 Component 패널에서 수정한다 |
| 인스턴스 스왑(Instance swap) | Component 패널의 'Create instance swap property' | 안쪽 square | Check box (Preferred values에 check-square) | 하위 인스턴스를 직접 선택하지 않고 상위에서 바꾼다 |

교재 TIP이 정리한 규칙은 두 가지다. 컴포넌트 프로퍼티는 메인 컴포넌트에서만 설정할 수 있고, 세 가지는 각각 다른 위치에서만 설정할 수 있다. 불리언은 0과 1만으로 참과 거짓을 나타내는 방식에서 온 이름이다.

![체크리스트: 프로퍼티만 바꿔 만든 세 항목]({{ '/assets/images/club-ecc-ux-ui/figma-p5-checklist.png' | relative_url }})

세 항목은 같은 check-list의 인스턴스이고 Component 패널의 프로퍼티만 다르다. 첫 항목은 Title과 Detail 텍스트만 바꿨다. 둘째 항목은 Title과 Detail을 바꾸고 Check box를 check-square로 스왑했다. 셋째 항목은 Show Detail을 꺼서 상세 내용이 사라졌고 그만큼 항목 높이가 줄었다. 안쪽 레이어를 한 번도 직접 선택하지 않고 만든 결과다.

프로퍼티의 순서는 메인의 Properties 패널에서 드래그로 바꾸고, 'Edit' 아이콘으로 이름과 값을 고치고, '−' 아이콘으로 지운다.

### 4장. 메인 컴포넌트의 묶음, 배리언츠 활용하기

> 배리언츠는 메인 컴포넌트들로 이루어진 컴포넌트 세트다.

여기서 프로퍼티는 컴포넌트의 상태를 구분하도록 임의로 지정하는 상태값이다. 버튼을 높이에 따라 S·M·L로, 색에 따라 빨강·파랑·초록으로 나눈다면 '크기'와 '컬러'가 프로퍼티다.

| 단계 | 할 일 | 수치·결과 |
| --- | --- | --- |
| 준비 | 100×100 프레임 3개(FF5555, 5588FF, FFBB55)를 아래로 두 번 복제. 둘째 행 Corner radius 24, 셋째 행 50 | 9개 |
| 묶기 ① | Create multiple components → Components 패널의 〈Combine as variants〉 | 이미 만든 컴포넌트를 묶을 때 |
| 묶기 ② | Create component 확장 메뉴 → Create component set | 처음부터 배리언츠로 설계할 때 |
| 이름 | `Ctrl+R` | '배리언츠 예제' (9 Variants) |
| 프로퍼티 1 | 'Property 1'을 더블클릭해 'Color'로. 열마다 선택해 밸류 입력 | red, blue, yellow |
| 프로퍼티 2 | Properties 패널 '+' → Variant → Name 'Radius', Value '0'. 둘째·셋째 행의 밸류 수정 | 0, 24, Max |

배리언츠가 만들어지면 메인 컴포넌트들이 보라색 점선의 배리언츠 프레임으로 감싸진다. 이 프레임은 일반 프레임과 같은 성질이라 크기를 조정하거나 오토 레이아웃을 걸 수 있다.

프로퍼티가 하나일 때 생기는 일이 이 장에서 볼 대목이다. Color만으로는 9개를 구분할 수 없어서 같은 밸류를 가진 배리언트끼리 충돌한다는 경고가 뜬다. Radius를 추가해 두 프로퍼티의 조합이 겹치지 않게 되어야 경고가 사라진다. 셋째 행을 '50'이 아니라 'Max'로 적는 것은 완전히 둥근 형태라는 뜻을 드러내기 위해서다.

![배리언츠 예제 9 Variants와 프로퍼티로 불러온 인스턴스]({{ '/assets/images/club-ecc-ux-ui/figma-p5-variants.png' | relative_url }})

왼쪽 보라색 점선 안이 배리언츠 프레임이고, 가로가 Color, 세로가 Radius다. 오른쪽 둘은 밖으로 복제한 인스턴스에서 Component 패널의 프로퍼티만 바꾼 것이다. 위는 Color red·Radius 24, 아래는 Color yellow·Radius Max다. 프로퍼티를 정하기 전에는 목록이 'Frame 1~9'로만 보였는데, 이제 색과 모양으로 원하는 컴포넌트를 바로 부른다.

프로퍼티와 밸류의 순서는 Properties 패널에서 드래그하거나 'Edit property'로 바꾼다. 배리언츠를 해제하려면 프레임에서 `Enter`로 내부 컴포넌트를 모두 선택해 밖으로 드래그한다. 모두 빠지면 배리언츠 프레임은 자동으로 삭제된다. 이때 컴포넌트 이름이 '배리언츠 예제/blue/24'처럼 '/'로 구분되어 남아서, 다시 배리언츠로 묶어도 프로퍼티 밸류가 살아 있다.

### 5장. 배리언츠 프로퍼티를 토글 형태로 만들기

칩(Chip)은 정보 입력, 선택, 내용 필터링에 쓰는 디자인 컴포넌트다.

| 단계 | 할 일 | 수치·설정 |
| --- | --- | --- |
| 01~03 | 'Chip' 텍스트(Medium 14) → `Shift+A` → Fill FFFFFF, Stroke DEDEDE → 'Chips' → 패딩과 Corner radius | H padding 16, 가운데, Radius 20 이상 (62×40) |
| 04 | 아래로 복제해 선택된 상태로 | 프레임 5162F8, 텍스트 FFFFFF |
| 05~08 | 둘을 Create component set → 'Property 1'을 'Selected'로 → 밸류 | false / true |
| 09~10 | 인스턴스를 밖으로 복제 | Component 패널에 Selected가 토글로 나온다 |

두 가지 상태로 구분되는 배리언츠는 밸류를 True/False, On/Off, Yes/No 중 하나로 지정하면 프로퍼티가 토글 형태가 된다. 주로 체크박스나 라디오 버튼 배리언츠에 쓴다.

이 칩으로 카테고리 목록을 만든다. 인스턴스 두 개를 `Shift+A`로 묶고 방향을 Wrap으로 바꾼 'Category'(간격 8) 안에서 칩을 `Ctrl+D`로 늘린 다음, `Ctrl`을 누른 채 텍스트를 더블클릭해 내용을 넣고 일부 칩의 토글을 켠다.

![Chips 배리언츠와 Wrap으로 만든 카테고리 목록]({{ '/assets/images/club-ecc-ux-ui/figma-p5-chips.png' | relative_url }})

왼쪽이 false와 true 두 배리언트로 된 Chips, 오른쪽이 인스턴스 아홉 개로 만든 Category다. 칩마다 글자 수가 달라도 프레임이 Hug라서 너비가 알아서 맞고, Category가 Wrap이라서 한 줄에 다 들어가지 않는 칩은 다음 줄로 내려갔다. 선택된 칩 네 개는 색을 직접 칠한 것이 아니라 Selected 토글만 켠 것이다. 3장의 불리언 프로퍼티도 토글이었지만 그쪽은 레이어 하나를 보이고 숨기는 것이고, 이쪽은 배리언트 자체를 다른 것으로 바꾸는 것이다. 교재 수치는 Category 너비 272이지만 Figma 파일에서는 한 줄에 세 개가 들어가도록 360으로 넓혔다.

### 6장. 버튼 배리언츠 구성하기

마지막 장은 컴포넌트 프로퍼티와 배리언츠 프로퍼티를 함께 써서 버튼 세트를 만든다.

먼저 Feather Icons에서 minus, plus, chevron 네 방향을 불러와 면으로 바꾸고 레이어 이름을 모두 'Vector'로 통일한 뒤 각각 컴포넌트로 만든다. 이름을 통일하는 이유가 Why?에 있다. 레이어 이름이 같아야 컴포넌트를 스왑할 때 아이콘의 변경된 색상을 유지한 채로 바뀐다.

기본 버튼은 '버튼'(Semibold 14)에 간격 4, 패딩 24/8, Corner radius 8을 주고 plus와 chevron-right 아이콘(16×16)을 양쪽에 넣는다. 이것을 복제해 여덟 개를 만든다.

| State | primary 버튼 | primary 글자·아이콘 | secondary 버튼 | secondary 글자·아이콘 |
| --- | --- | --- | --- | --- |
| default | 622EEE | FFFFFF | EEEEF1 | 6B6A6F |
| hover | 521CE3 | FFFFFF | E3E3E8 | 6B6A6F |
| active | 4B1DC9 | FFFFFF | D7D7DF | 6B6A6F |
| disabled | E2DDFD | FFFFFF | F4F4F6 | CCCBCF |

Primary는 구매하기나 확인처럼 중요도가 높고 긍정적인 곳에 쓰는 버튼이고, Secondary는 취소나 닫기처럼 그보다 중요도가 낮은 곳에 쓴다. Hover는 마우스 커서가 버튼 위에 있는 상태라서 PC 환경에서만 확인할 수 있다. 여러 버튼의 글자와 아이콘 색을 한 번에 바꿀 때는 Selection colors 패널을 쓴다. 선택 영역 안의 같은 색을 한 번에 바꿔 준다.

여덟 개를 Create component set으로 묶고 프로퍼티를 쌓는다.

| 프로퍼티 | 종류 | 밸류·기본값 | 만드는 법 |
| --- | --- | --- | --- |
| Type | Variant | primary, secondary | 기본 프로퍼티 이름 변경 후 열마다 입력 |
| State | Variant | default, hover, active, disabled | Properties '+' → Variant, 행마다 입력 |
| Show left icon | Boolean | True | plus 선택 → 'Select matching layer' → Layer 패널 |
| Left icon | Instance swap | plus (Preferred: minus) | Component 패널 |
| Show right icon | Boolean | True | chevron-right에 같은 방법 |
| Right icon | Instance swap | chevron-right (Preferred: down, left, up) | Component 패널 |
| Label | Text | 버튼 | 텍스트에 같은 방법 → Text 패널 |
| Size | Variant | S, M, L | Properties '+' → Variant. 8개를 복제해 Vertical padding 12(높이 48), 16(높이 56) |

'Select matching layer'는 배리언츠 안에서 같은 오브젝트를 한 번에 선택해 준다. 덕분에 여덟 개 버튼의 plus 아이콘에 프로퍼티를 한 번에 걸 수 있다.

![button 배리언츠 24 Variants와 프로퍼티로 만든 인스턴스]({{ '/assets/images/club-ecc-ux-ui/figma-p5-button-variants.png' | relative_url }})

위 점선 프레임이 완성된 배리언츠다. 왼쪽부터 Size S, M, L이고, 각 묶음 안에서 왼쪽 열이 primary, 오른쪽 열이 secondary, 위에서 아래로 default, hover, active, disabled다. 아랫줄은 인스턴스 여섯 개다. '+ 더하기'는 오른쪽 아이콘을 끄고, '바로가기 >'는 왼쪽 아이콘을 끄고, '취소'와 '확인'은 둘 다 껐다. '− 빼기'는 Left icon을 minus로, Right icon을 chevron-down으로 스왑했다. 마지막 흐린 버튼은 State를 disabled로 바꾼 것이다. 여섯 개 모두 여덟 프로퍼티의 값만 다르다.

장의 마지막 Why?가 두 프로퍼티를 나눠 쓰는 이유를 숫자로 보여 준다.

| 구성 | 계산 | 컴포넌트 수 |
| --- | --- | --- |
| 예제 버튼 배리언츠 | 2 형태 × 4 상태 × 3 크기 | 24개 |
| 컴포넌트 프로퍼티 없이 | 24 × 아이콘 4경우(왼쪽만, 오른쪽만, 둘 다, 없음) | 96개 |

아이콘 유무까지 배리언트로 만들면 96개가 필요한데, 불리언 프로퍼티 두 개로 처리해서 24개로 줄였다. 버튼 내부 요소에 컴포넌트 프로퍼티, 특히 불리언 프로퍼티를 적절히 쓰면 배리언츠 볼륨을 크게 줄일 수 있다는 것이 Why?의 결론이다.

## 정리

3부 4장 워크플로와 정보 구조에서 기억할 것.

- 3부의 1~3장은 UX에 가까운 방법, 4장은 UI에 가까운 방법이다
- 인터랙티브 시스템은 시스템, 서비스(=기능), 메뉴 구조와 워크플로, 스크린으로 구성된다. 정보 구조는 정적이고 메뉴 구조와 워크플로는 동적이다
- 워크플로는 한 태스크의 순차적인 조작 절차이고 정보 구조 유형으로는 선형이다. 하나의 화면은 하나의 경로로만 연결되지 않는다
- 워크플로의 추상성은 단어, 와이어프레임 스케치, 스크린숏 순으로 구체적이다
- 유저플로는 모든 경로, 해피 패스는 그중 오류와 예외가 없는 하나의 경로다
- 정보 구조 유형은 선형, 그리드형, 계층형, 그물형, 링형, 스타형과 이들을 결합한 하이브리드형이다. 쏘카는 계층 구조에 예약·결제·반납의 선형 구조를 결합했다
- 정보 구조를 고를 때는 사용자의 요구, 정보의 유형, 유연성과 확장성, 효율성을 본다. 스마트폰 이후 사용자 통제권이 확대되어 정보 구조는 유동적인 형태가 되었다
- 메뉴 설계는 여덟 단계이고, 넓고 얕은 구조가 좁고 깊은 구조보다 대체로 바람직하다
- 카드소팅의 개방형은 카드를 모은 뒤 카테고리를 정하는 상향식, 폐쇄형은 카테고리를 주고 카드를 배치하는 하향식이다

PART 5 컴포넌트와 배리언츠에서 기억할 것.

- 메인 컴포넌트는 기본 속성을 정의하고 인스턴스는 디자인에 쓴다. 메인은 별도 페이지에서 관리한다
- 인스턴스에서 바꾼 속성은 메인의 영향을 받지 않는다. 색을 다시 같게 맞춰도 풀리지 않고 Reset으로 초기화해야 한다
- 아이콘은 배리언츠로 묶지 않고 각각 컴포넌트로 관리한다. 이름에 '/'를 넣으면 폴더로 그룹화된다
- 컴포넌트 프로퍼티는 메인에서만 설정한다. 불리언은 Layer 패널, 텍스트는 Text 패널, 인스턴스 스왑은 Component 패널에서 만든다
- 배리언츠는 메인 컴포넌트의 세트다. 프로퍼티 조합이 겹치면 충돌 경고가 뜬다
- 밸류를 True/False, On/Off, Yes/No로 지정하면 배리언츠 프로퍼티가 토글이 된다
- 버튼 배리언츠는 2 형태 × 4 상태 × 3 크기로 24개다. 아이콘 유무를 불리언 프로퍼티로 처리하지 않았다면 96개가 필요했다
