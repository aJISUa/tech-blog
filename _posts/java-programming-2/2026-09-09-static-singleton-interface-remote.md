## static

static은 `new`로 객체를 만들지 않아도 쓸 수 있는 멤버다.

일반(non-static) 멤버는 객체마다 따로 생기고, 객체를 만든 다음에야 쓸 수 있고, 다른 객체랑 공유되지 않는다. 반면 static 멤버는 클래스당 딱 하나만 있고, 클래스가 로딩될 때 static 영역에 올라가고, 그 클래스로 만든 객체들이 다 같이 쓴다.

```java
StaticSample.f();   // static 메소드는 클래스 이름으로 바로 호출
```

교수님께서는 static을 붙이면 클래스 설계도 자체가 하나의 객체처럼 올라간다고 설명하셨다. `Math.abs(-5)`처럼 전역 변수, 전역 함수를 만들 때 쓴다. (`Math`는 생성자가 private이라 `new Math()`가 안 된다.)

static 메소드 안에서는 `this`를 못 쓰고 일반 멤버에도 접근할 수 없다. 객체가 아직 없을 수도 있으니까. 반대로 일반 메소드에서는 static 멤버를 쓸 수 있다.

## final

final은 "최종"이라는 뜻이고, 한 번 정하면 못 바꾸게 막는다. 어디에 붙이냐에 따라 의미가 조금씩 다르다.

- 클래스에 붙이면 상속을 못 한다. "나 건드리지 마"
- 메소드에 붙이면 오버라이딩을 못 한다. "나 그냥 내버려 둬"
- 필드에 붙이면 상수가 된다. 선언할 때 값을 넣어야 하고 실행 중에는 못 바꾼다.

```java
class SharedClass {
    public static final double PI = 3.14;   // 모두 같이 쓰는 상수
}
```

## 싱글톤: 딱 하나만 만드는 객체

하늘은 몇 개일까? 하나다. 지구도 하나다. 이렇게 프로그램 전체에서 딱 하나만 만들고 모두가 같이 써야 하는 객체를 싱글톤이라고 한다.

요즘은 예시 들 게 없다고 하셨다. 옛날에는 집에 TV가 한 대였는데 요즘은 방마다 있다고. 그나마 프린터는 집에 한 대라서 예시로 들 만하다고 하셨다. 그리고 실제로 우리가 쓰는 서비스는 대부분 싱글톤으로 만들어져 있다고 한다.

### 만드는 순서

1. 객체가 만들어졌는지 저장해둘 `private static` 변수를 만든다. 보통 이름은 `instance`고, 처음엔 아무것도 없으니까 `null`
2. 생성자를 `private`으로 바꿔서 밖에서 `new`를 못 하게 막는다
3. 아직 없으면 새로 만들고, 이미 있으면 있는 걸 돌려주는 `public static getInstance()`를 만든다

### Lab #3: 하늘 만들기

```java
public class 하늘 {
    // 1. 하늘 객체를 저장할 변수 (다 같이 쓰고, 밖에서는 못 건드림)
    private static 하늘 instance = null;

    // 2. 생성자를 private으로
    private 하늘() {
        System.out.println("하늘 객체를 만듭니다.");
    }

    // 3. 밖에서 부를 수 있는 getInstance()
    public static 하늘 getInstance() {
        if (instance == null) {       // 아직 없으면
            instance = new 하늘();     // 만들어서 저장하고
        }
        return instance;              // 있으면 있는 거 돌려주기
    }
}
```

```java
public class Main {
    public static void main(String[] args) {
        // 하늘 sky = new 하늘();   // 빨간 줄. 생성자가 private이라 밖에서 안 보인다

        하늘 sky1 = 하늘.getInstance();   // 클래스 이름으로 부른다
        하늘 sky2 = 하늘.getInstance();
        하늘 sky3 = 하늘.getInstance();

        System.out.println(sky1);
        System.out.println(sky2);
        System.out.println(sky3);
    }
}
```

```text
하늘 객체를 만듭니다.
하늘@1b6d3586
하늘@1b6d3586
하늘@1b6d3586
```

(@ 뒤의 값은 실행할 때마다 달라진다. 위 값은 예시다.)

"하늘 객체를 만듭니다."는 한 번만 찍히고, @ 뒤에 나오는 해시코드도 셋 다 같다. 객체마다 붙는 식별값(hashCode)이라 메모리 주소는 아니지만, 이 값이 같으면 같은 객체로 봐도 된다. `getInstance()`를 몇 번을 불러도 새로 안 만든다.

처음부터 하나 만들어두고 절대 안 바꾸고 싶으면 `private static final 하늘 instance = new 하늘();`처럼 final을 붙이기도 한다. 싱글톤 만드는 방법은 여러 가지고, 오늘 한 건 그중 흔한 방법 하나다. 4~5주차에 디자인 패턴을 배우는데 그중 제일 쉬운 게 싱글톤이라고 하셨다.

근데 현업에서는 싱글톤이 테스트할 때 골치 아프다고 한다. 하나만 있어야 하는데 실제 서비스용이랑 테스트용이 따로 필요하니까. 이건 소프트웨어공학에서 테스트 기법 배울 때 다시 나온다고 하셨다.

## 추상 클래스와 인터페이스는 목적이 같다

교수님께서 딱 잘라서 말씀하셨다. 추상 클래스랑 인터페이스는 목적이 똑같고, 하나는 클래스고 하나는 인터페이스라는 이름만 다르다고.

둘 다 객체를 만들려고 쓰는 게 아니라 참조하려고 쓴다. `new`로 못 만들고, 업캐스팅용으로 계층을 만든다. 설계랑 구현을 나눠서 다형성을 쓸 수 있게 해준다는 점도 같다.

### 언제 뭘 쓰나

이미 다른 클래스를 상속받은 상태라면 또 상속할 수 없으니까 무조건 인터페이스를 쓴다.

"나는 일반 클래스가 아니라 상속받으라고 만든 클래스다" 싶고, 아직 구체적으로 다 정해지지 않았으면 추상 클래스를 쓴다. 예를 들어 도형 클래스에는 "넓이를 구하는 메소드가 있어야 한다"까지만 정해두고, 넓이 구하는 방법은 도형마다 다르니까 자식 클래스에서 만든다.

생각해보면 세상에 "동물"이나 "탈것"이라는 물건 자체는 없다. 호랑이를 동물이라고 부르고 비행기를 탈것이라고 부를 뿐이다. 그래서 이런 건 추상 클래스로 만드는 게 의미상 더 맞을 때가 있다.

### 비교

| | 추상 클래스 | 인터페이스 |
| --- | --- | --- |
| 추상 메소드 | O | O |
| 구현된 메소드 | O | default 메소드로 O |
| static 메소드 | O | O |
| 일반 필드(변수) | O | X (상수만) |
| 여러 개 상속 | X | O |

```java
public abstract class Shape {         // 추상 메소드가 있으면 abstract class로
    public void paint() { draw(); }
    public abstract void draw();       // 몸통 없이 선언만
}
Shape s = new Shape();                 // 컴파일 에러
```

추상 메소드가 하나도 없어도 `abstract class`로 선언할 수 있고, 그래도 `new`는 안 된다.

## 인터페이스로 업캐스팅

```java
RemoteControl rc = new Television();
rc.turnOn();    // Television의 turnOn()
rc = new Audio();
rc.turnOn();    // Audio의 turnOn()
```

인터페이스는 만들 수는 없고 참조만 할 수 있다. 구현한 객체를 인터페이스 변수에 넣으면 자동으로 형변환이 된다. 클래스에 기능이 아무리 많아도 인터페이스에 적힌 것만 보인다.

반대로 안 되는 경우도 있다. 부모로 만든 객체를 자식 타입 변수로 받으려고 할 때(`자식 c = new 부모();`), 그리고 아예 상속 관계가 아닌데 참조하려고 할 때.

### Lab #4: 인터페이스 상속과 구현

```java
interface A { void a(); }
interface B { void b(); }
interface C extends A, B { void c(); }   // 인터페이스는 여러 개 상속 가능

class E { void e() { System.out.println("E"); } }

class D extends E implements C {         // E를 상속하고 C를 구현
    public void a() { System.out.println("A 기능"); }
    public void b() { System.out.println("B 기능"); }
    public void c() { System.out.println("C 기능"); }
}
```

C가 A랑 B를 상속하고 있으니까 D는 A, B, C의 메소드를 전부 구현해야 한다.

현실로 바꿔보면 D는 스마트폰이다. 전화, MP3, 이메일 기능(인터페이스)을 구현하고, 컴퓨터나 전자기기(클래스 E)를 상속받은 것. D를 학생이라고 하면 사람(E)을 상속받고, 공부하기, 질문하기(인터페이스)를 꼭 구현하라고 정해둘 수 있다.

코드 칠 때 팁도 하나 주셨다. 괄호를 열자마자 엔터 치지 말고 일단 닫아놓고 안을 채우라고. 그리고 메소드 안에는 출력문 하나만 넣어도 충분하다고.

## Lab #5: 리모컨 만들기

### 요구사항

- TV, Audio, Car가 있고 전부 리모컨으로 조작한다
- 기능은 전원 켜기, 끄기, 음소거. 자신 있으면 볼륨 올리기, 내리기도
- Car는 전원 켜기, 끄기가 시동 걸기, 끄기다
- 리모컨은 딱 하나다. 그러니까 싱글톤으로 만들면 좋다
- 조작할 기기나 기능은 나중에 더 늘어날 수 있다 (청소기, 에어컨 등)

실제 리모컨은 안 쓰는 버튼이 엄청 많은데, 우리는 전원이랑 볼륨 정도만 앞에 두고 나머지는 숨긴 간단한 리모컨을 만든다. 리모컨 하나로 여러 기기를 조작하려면 TV, Audio, Car를 바꾸는 버튼을 두면 된다.

### 구조

- `RemoteControl` 인터페이스에 `turnOn()`, `turnOff()`, `setMute()` 같은 기능을 정의한다
  - 모든 기기가 똑같이 동작하는 기능은 자식마다 복붙하지 말고 default 메소드로 만든다
  - 최대 볼륨, 최소 볼륨 같은 값은 상수로 둔다
- `Television`, `Audio`, `Car`가 `RemoteControl`을 구현한다
- `MyRemoteControl` 클래스는 리모컨 하나로 여러 기기를 조작해야 하니까 `RemoteControl rc` 필드를 갖는다

### 기기 바꾸는 메소드는 어떻게 만들까

방법 1은 Object 하나로 받아서 if문으로 나누는 거다.

```java
public void changeMode(Object device) {
    if (device instanceof Television) {
        rc = (Television) device;
    } else if (device instanceof Audio) {
        rc = (Audio) device;
    }
    // 자동차가 추가되면? 이 메소드를 열어서 else if를 끼워 넣어야 한다
}
```

방법 2는 받는 타입별로 오버로딩하는 거다.

```java
public void changeMode(Television tv) { rc = tv; }
public void changeMode(Audio audio)   { rc = audio; }
public void changeMode(Car car)       { rc = car; }   // 기기가 늘어나면 메소드만 하나 추가
```

1학년한테 물어보면 "1번은 비교문도 있고 뭔가 멋있어 보이는데 2번은 너무 단순해요"라고 한다고 한다. 근데 답은 2번이다.

1번은 기기가 하나 늘어날 때마다 이미 만든 메소드를 뜯어서 안쪽을 고쳐야 한다. 교수님 표현으로는 부품을 갈라서 속을 쪼개고 바느질하는 것. 2번은 부품을 하나 더 연결하기만 하면 된다. 메소드가 작고 튼튼해서 모듈화가 잘 되고 OOP에도 더 맞다.

이게 SOLID의 OCP(개방-폐쇄 원칙)고, 패턴으로 보면 전략 패턴이라고 하셨다. 기존 코드는 안 고치고 새 기능은 추가할 수 있게 만드는 것.

다만 2번도 기기가 늘어나면 리모컨 클래스에 메소드를 추가해야 하니까, 엄밀히 말하면 리모컨은 여전히 고쳐진다. 인터페이스 타입 하나로 받는 `changeMode(RemoteControl device)`까지 가면 기기가 늘어나도 리모컨은 손댈 일이 없다. 이건 나중에 Vehicle-Driver 리팩토링에서 `drive(Moveable m)` 하나로 줄이면서 다시 느꼈다.

솔루션 코드는 테스트용이라 완벽하지 않다고 하셨다. 노션 코드를 복붙하지 말고, 몇 줄 안 되니까 직접 치면서 인터페이스가 이런 식으로 쓰이는구나 느껴보라고.

## 배틀 리팩토링 과제 안내

지난 학기 자프실1 배틀 프로젝트 코드를 받아서 리팩토링 관점으로 분석하는 과제다.

완벽한 게임을 새로 만들라는 게 아니다. 설계가 잘못된 곳을 찾고, 어떻게 고치면 될지 분석하고, 알게 된 점이랑 궁금한 점을 정리하는 거다. AI한테 시키지 말고 직접 하라고 하셨다.

### 받은 코드 힌트

- 1번: 상속을 잘못 쓴 코드
- 2번: 이것도 상속을 잘못 썼는데 1번이랑 다른 방식으로
- 3번: 모듈화가 안 돼 있고 if문이 엄청 많다 (멋있어 보이는 게 아니다)
- 실행은 너무 잘 된다. 근데 열어보면 심각한 문제가 있다

### 이클립스로 가져오는 법

1. 압축을 푼다. 압축 안에 압축이 또 있어서 한 번 더 풀어야 한다
2. Package Explorer에서 우클릭 → `Import → General → Existing Projects into Workspace`
3. `Select root directory`에서 푼 폴더(예: `RTK배틀`)를 고르고 Finish
4. 코드 하나 열어서 한글 깨지는지 확인. 깨지면 UTF-8이랑 MS949를 바꿔본다

### PlantUML로 구조 보기

패키지가 여러 개라 전부 선택하면 너무 복잡하니까 보고 싶은 클래스만 골라서 봤다.

- Player와 유비: Player에 속성을 만들어뒀는데 `private`이라 안 보이니까 자식인 유비에서 똑같이 또 선언했다. getter/setter를 추가했어야 하는, 상속을 잘못 쓴 경우다.
- Player와 무기: 플레이어가 무기를 쓰니까 association 관계다.
- 무기와 하위 무기 클래스(장팔사모 등): 부모인 무기에 데미지 속성이 있는데 자식에서 또 선언했다. 이것도 상속을 잘못 쓴 경우.

뭐가 문제인지 찾고 어떻게 고칠 수 있는지 분석하는 게 목표다. 구글 시트 가이드대로 현재 상태, 고칠 부분, 고친 후, 알게 된 점, 궁금한 점 순서로 정리하면 된다.

## 정리

- static은 클래스당 하나만 있고 다 같이 쓴다. final은 못 바꾸게 막는다(상속, 오버라이딩, 값)
- 싱글톤은 `private static instance`, `private` 생성자, `public static getInstance()` 세 개면 만들 수 있다
- 추상 클래스와 인터페이스는 목적이 같다. 만드는 용도가 아니라 참조하는 용도고, 계층을 만든다
- 인터페이스는 `new`는 안 되지만 업캐스팅은 된다
- 기능이 늘어날 때 기존 코드를 뜯어야 하는 구조보다 메소드만 추가하면 되는 구조가 좋다
