## PlantUML은 왜 쓰나

PlantUML은 글(스크립트)로 다이어그램을 그리는 도구다. 클래스 다이어그램, 시퀀스 다이어그램 같은 걸 다 그릴 수 있고, 이클립스에 플러그인으로 깔면 `Window → Show View → PlantUML`에서 패키지나 파일만 클릭해도 구조도가 바로 나온다.

교수님께서 든 예시가 와닿았다. 설계도도 문서도 안 남기고 퇴사한 사람의 코드를 받았다고 치면, 처음부터 코드를 한 줄씩 읽을 수는 없다. 그래서 먼저 전체 배치를 보고(5층짜리 건물 하나인지, 건물이 여러 채인지), 그다음에 중요한 클래스들끼리 어떤 관계인지만 골라서 본다.

처음 설계할 때는 드래그 앤 드롭이 편한 Amateras를, 이미 있는 코드를 파악할 때는 PlantUML을 쓰면 된다.

### UML 표기는 다 외울 필요 없다

| 관계 | 표기 | 뜻 |
| --- | --- | --- |
| 상속 (extends) | 실선 + 빈 삼각형 `──▷` | is-a |
| 구현 (implements) | 점선 + 빈 삼각형 `┈┈▷` | 기능 구현 |
| 연관 (association) | 실선 화살표 `──>` | 사용한다, 갖고 있다 |
| 집합, 합성 | 다이아몬드 `◇──`, `◆──` | 소유한다 |

옛날에는 이런 표기를 수십 개씩 외우게 했는데 요즘은 최대한 단순하게 그린다고 하셨다. 모르겠으면 선 하나 긋고 위에 `<<uses>>`처럼 써도 다 알아본다. 툴마다 그리는 방식도 조금씩 달라서 읽을 줄만 알면 된다.

합성(◆)은 콘크리트 본드로 붙여둔 것처럼 떼기가 어려운 강한 결합이다. 요즘은 블록처럼 끼웠다 뺐다 할 수 있는 약한 결합을 선호한다. 그래서 이번 학기에는 상속을 쓰는 법보다 상속을 피하는 법을 배운다고 하셨다.

## 요구사항 읽는 법

코드부터 떠올리지 말고 내가 만들 객체부터 떠올린다.

- 이 객체가 무엇을 알고 있어야 하나? → 필드
- 무엇을 할 수 있어야 하나? → 메소드
- 누구의 하위 클래스로 두면 좋을까? 같은 동작은 뭐고 다른 동작은 뭘까?

교수님 말로는 프로그래밍 언어도 결국 언어라서, 주어는 객체, 동사는 메소드, 목적어는 파라미터로 생각하면 쉽다고 했다.

### Vehicle-Driver 요구사항 뜯어보기

**"Driver는 여러 Vehicle을 운전할 수 있다. 그러나 소유한 것은 아니다."**
이게 제일 중요한 문장이었다. 소유하지 않으니까 Driver 필드에 Vehicle이 없어야 하고, `drive(Vehicle v)`처럼 파라미터로 받아서 운전해야 한다.

**"모든 Vehicle의 이동 단위는 10km, 연료는 연비로 계산한다(10km당 연료 = 10/연비)."**
연비가 12, 0.1, 4처럼 소수도 있으니까 연비랑 연료량은 double로 잡아야 한다.

**"Vehicle은 Moveable 가능하다."**
이름이 -able로 끝나면 보통 인터페이스다. `class Vehicle implements Moveable`. 인터페이스 이름에는 -able을 붙이거나 앞에 I를 붙이는 경우가 많은데, 안 붙여도 에러는 아니지만 붙이면 읽기 편하다.

**"버스는 부릉부릉, 비행기는 슝, 탱크는 탱크탱크. 연료가 줄어드는 건 똑같다."**
똑같은 부분은 부모에 두고, 다른 부분은 오버라이딩하면 된다.

**"Driver는 총 주행거리를 저장한다."**
그래서 Driver 필드는 `name`이랑 `distance`.

**drive(버스), drive(탱크), drive(Vehicle)...**
이름은 같고 파라미터만 다르니까 오버로딩이다.

## 퀴즈 풀이

### 0번. A는 B를 확장하고 C, D를 구현한다. E는 A 타입 객체를 갖는다

```java
public class A extends B implements C, D
```

그림으로 그리면 A에서 B로는 실선 삼각형(상속), A에서 C, D로는 점선 삼각형(구현), E에서 A로는 실선 화살표나 E 쪽에 다이아몬드(소유)다. 코드 문법보다 그림으로 먼저 이해하라고 하셨다.

### 1번. Vehicle 클래스의 속성 4개

```java
public String name;      // 외부에서 볼 수 있는 건 이름뿐
private double 연료량;    // 연비가 소수라서 연료 계산 결과도 소수
private int 주행거리;     // 10km씩 늘어나니까 정수
private double 연비;      // 0.1 같은 값이 있음
```

사실 나는 처음에 `int 연료량`, `double 주행거리`로 반대로 골랐다. 연료는 10km/연비만큼 줄어드니까 소수가 나오고, 주행거리는 10씩 늘어나니까 정수가 맞다.

### 2번. Driver 클래스의 속성 2개

`String name`이랑 총 주행거리 `distance`. 여기서 Vehicle을 고르면 틀린다. 소유하지 않는다고 했으니까. 클래스 다이어그램을 보면 `distance`는 int다.

### 3번. drive() 메소드를 어떻게 정의할 수 있나

파라미터가 있는 건 전부 된다.

```java
void drive(Vehicle v)
void drive(버스 b)
void drive(비행기 a)
void drive(탱크 t)
void drive(Moveable m)
void drive(Vehicle[] vs)
void drive(Moveable[] ms)
```

"미미는 Vehicle을 운전한다", "버스를 운전한다", "움직일 수 있는 걸 운전한다" 다 말이 된다.

### 4번. Vehicle 클래스 헤더

```java
class Vehicle implements Moveable
```

인터페이스에 연결한다는 건 그 기능을 반드시 구현해야 한다는 뜻이다. 그래서 인터페이스를 보면 "이 클래스는 이런 기능이 있겠구나" 하고 사용 설명서처럼 읽을 수 있다.

클래스 상속은 한 번만 된다(`extends Machine, AA`는 안 됨). 인터페이스 구현은 `implements Moveable, Flyable`처럼 여러 개 된다.

### 5번. 같은 동작(연료 감소)과 다른 동작(소리)은 어디에 둘까

답은 1번이랑 4번이다.

1. 공통 동작은 Vehicle의 `move()`에 구현해서 물려준다. (O)
2. 부모 메소드를 전부 static으로 만든다. (X) static은 이러라고 있는 게 아니다. static 영역에 올라가서 모두가 같이 쓰는 용도다.
3. 하위 클래스마다 코드를 복사해서 쓴다. (X) 앞부분은 괜찮은데 복사한다는 게 틀렸다.
4. 각자 다른 동작은 하위 `move()`에서 하고, 공통 동작은 `super.move()`를 부른다. (O)

```java
public class 버스 extends Vehicle {
    public int move() {
        운행하기();            // "부릉부릉부르릉~~" (버스만의 동작)
        return super.move();   // 연료 감소, 주행거리 증가 (공통 동작)
    }
}
```

오버라이딩이랑 오버로딩은 헷갈리면 안 된다. 오버라이딩은 상속받은 메소드를 내 식으로 다시 만드는 거고, 오버로딩은 같은 이름으로 파라미터만 다르게 여러 개 만드는 거다.

### 6번. "Driveable한 d는 Moveable한 m을 drive한다"

```java
((Driveable) d).drive(m)
```

`(Driveable)d.drive(m)`이라고 쓰면 점(.)이 먼저 계산돼서 `d.drive(m)`의 결과를 형변환하는 게 된다. `drive`는 리턴 타입이 void라 형변환할 것도 없어서 항상 컴파일 에러다. "Driveable한 d"까지가 주어니까 괄호로 한 번 더 감싸야 한다.

단, 괄호를 맞게 써도 이 코드가 바로 돌아가는 건 아니다. 솔루션의 `Driveable`에는 인자 없는 `drive()`만 있어서, Driveable 타입으로 보면 `drive(m)`이 안 보인다. 인터페이스에 `drive(Moveable m)`을 적어둬야 컴파일이 된다. 이건 2주차 과제에서 직접 확인했다.

### 8번. 꼭 static이어야 하는 메소드

`show(Vehicle[] vs)`. 메인에서 `Vehicle.show(vs)`처럼 객체 없이 클래스 이름으로 바로 부르고 있기 때문이다.

### 9번. 인자 없는 d.drive()는?

요구사항에 없는 상황이다. 수업에서는 둘 중 하나로 하면 된다고 했다.

- 오버로딩을 안 해서 문법 에러로 잡히게 하기
- 오버로딩은 하되 "움직일 객체를 인자로 넣어주세요" 같은 안내 문구 출력하기

### drive(비행기 a)가 없으면 에러가 날까?

안 난다. 솔루션 코드는 `drive(ms[i])`로 부르기 때문에 실제로 돌려보면 전부 `drive(Moveable m)`으로 들어가서 "Moveable한 것을 운전합니다."가 찍힌다. 주석에 있는 `drive((비행기)ms[i])`처럼 비행기 타입으로 넘기면 아래 결과처럼 "Vehicle을 운전합니다."가 나온다.

```text
Moveable [] 한 ms를 drive합니다.
버스를 운전합니다.
부릉부릉부르릉~~
...
Vehicle을 운전합니다.
슈우우우웅~~
```

비행기 타입으로 넘겼는데 비행기를 받는 메소드가 없으면, 비행기를 Vehicle로 업캐스팅해서 `drive(Vehicle v)`를 찾아간다. 그것도 없으면 Moveable로 올라가고, 거기도 없어야 에러가 난다. 그래서 부모 타입을 받는 메소드를 하나 만들어두는 게 좋다.

## 실행 결과

| 차량 | 연료 | 연비 | 갈 수 있는 거리 |
| --- | --- | --- | --- |
| 타요버스 | 100 | 12 | 1200km |
| 쑝비행기 | 100 | 0.1 | 10km |
| 탱크탱크 | 50 | 4 | 200km |

그래서 미미의 총 주행거리는 1410km다.

### 솔루션 코드 보면서 알게 된 것

```java
public void drive(Moveable m) {
    System.out.println("Moveable한 것을 운전합니다.");
    distance += m.move();   // 각자 오버라이딩한 move()가 알아서 실행된다
}
```

`if (m instanceof 버스)`, `else if (m instanceof 비행기)` 이런 식으로 타입을 하나하나 비교할 필요가 없었다. 코드 주석에 "비교문이 있어야 코드 같다는 생각은 버려라"라고 적혀 있었다.

운전자 입장에서는 차를 버스, 탱크로 볼 필요 없이 "움직일 수 있는 것"으로만 보면 되니까 `drive(버스)`, `drive(탱크)`도 사실 없어도 된다. 그리고 `distance += ms[i].move()`도 동작은 하지만, 운전자가 운전한다는 의미를 살리려면 `drive(ms[i])`로 부르는 게 더 맞다.

## 한글이 깨졌을 때 (UTF-8, MS949)

교수님께서 올려주신 코드가 ANSI(MS949)로 저장돼 있어서, 이클립스가 UTF-8로 설정된 사람은 가져오면 한글 주석이 전부 깨진다.

- 확인하는 곳: 프로젝트 우클릭 → `Properties → Resource → Text file encoding`, 또는 `Window → Preferences → General → Workspace`
- 해결: 그 프로젝트만 인코딩을 `MS949`로 바꾼다. 목록에 없으면 직접 쳐서 넣으면 된다.
- 그래도 안 되면 메모장으로 열어서 복사해 붙여넣기

파일을 드래그해서 가져올 때는 Link 말고 Copy를 골라야 한다. 이거 몰라서 서너 시간 날리지 말라고 하셨다.

## 상속이랑 인터페이스는 왜 쓸까

상속은 기존 클래스를 다시 쓰고 싶을 때, 그리고 하위 클래스들을 하나로 묶어서(일반화해서) 다루고 싶을 때 쓴다.

인터페이스는 이유가 세 가지다.

1. 이 클래스가 어떤 기능을 반드시 구현해야 하는지 알려줄 수 있다. 구현 안 하면 에러가 나고, 역할이 분명해서 사용법처럼도 쓸 수 있다.
2. 기능 단위로 묶어서 부모 타입처럼 참조할 수 있다.
3. 기능이 많은 큰 클래스를 필요한 기능으로만 접근하게 할 수 있어서 캡슐화에도 좋다.

{: .notice--warning}
상속의 단점은 따로 조사해보라고 하셨다. 현업에서는 "상속 쓰지 말자"는 분위기인데, 정작 라이브러리를 열어보면 5단계씩 상속한 코드가 수두룩하다고. 조사한 내용은 9/9 OOP 복습 글에 적었다.

## 정리

- 요구사항 문장에서 주어는 객체, 동사는 메소드, 목적어는 파라미터
- "소유하지 않는다"면 필드가 아니라 파라미터로 받는다
- 같은 동작은 부모에, 다른 동작은 오버라이딩하고 `super.move()`
- 딱 맞는 오버로딩이 없으면 업캐스팅해서 부모 타입 메소드를 찾아간다
- 공부 기록은 "인터페이스는 이거다"보다 "배웠는데 까먹었다"에서 시작해도 괜찮다고 하셨다
