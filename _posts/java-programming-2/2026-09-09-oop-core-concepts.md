## OOP는 왜 쓰나

OOP(객체지향 프로그래밍)는 소프트웨어를 만드는 방식 중 하나고, 요즘은 C 같은 절차적 언어보다 OOP 언어로 개발하는 게 일반적이다. 쓰는 이유는 크게 두 가지다.

첫째는 빨리 만들기 위해서다. 상속, 다형성, 캡슐화처럼 코드를 다시 쓰기 좋은 장치가 있어서 빨리 만들 수 있고, 그걸 바탕으로 기능을 쌓거나 버전을 올리기도 쉽다.

둘째는 현실을 쉽게 옮기기 위해서다. 요즘 프로그램은 계산 절차보다 현실에서 일어나는 일을 다루는 경우가 많아서, 문제를 분석하고 어떤 객체가 있고 서로 어떤 관계인지를 먼저 파악해야 한다. 그리고 요구사항이 바뀌어도 빨리 대응할 수 있어야 한다.

객체는 데이터(필드)랑 기능(메소드)을 묶어놓은 거다. 부품 객체를 먼저 만들고 조립해 나가는 방식이라고 보면 된다.

## 캡슐화: 숨기고 보호하자

우리가 옷을 입고 피부가 장기를 보호하는 것처럼, 굳이 보여줄 필요 없는 건 감춘다. 학교에서도 학과랑 이름 정도만 알려주고 나머지는 말 안 하는 것처럼.

클래스를 만드는 것부터가 캡슐화의 시작이다. 필드랑 메소드를 클래스 안에 감싸니까. 거기에 더해서 외부에서 함부로 못 건드리게 접근 제한자를 쓴다.

예전에는 편하니까 다 `public`으로 만들었는데, 지금은 `private`이 기본이다. 일단 다 막아두고, 필요하면 getter/setter로 열어준다.

```java
private String 비밀번호 = "1357abcd/.,";   // 밖에서 직접 못 봄

String get비밀번호() {                      // getter: 값을 가져온다
    return this.비밀번호;
}
void set비밀번호(String 비번) {             // setter: 값을 넣는다
    this.비밀번호 = 비번;
}
```

필드가 3개면 메소드를 6개 만들어야 해서 귀찮긴 하다. 그래도 귀찮다고 `public`으로 풀지 말고 이클립스의 `Source → Generate Getters and Setters`를 쓰라고 하셨다. 개발자는 개발자가 해야 하는 일을 하고, 나머지는 도구한테 맡기면 된다고.

배틀 리팩토링 과제에서 제일 먼저 보이는 문제도 이거라고 하셨다. 부모 클래스에서 필드를 `private`으로 막아놨더니 자식에서 안 보이니까, 자식 클래스에 같은 필드를 또 선언해버린 것. 부모에 getter/setter만 추가했으면 됐다.

## 상속: 같은 부분은 다시 쓰자

상속은 공통 부분을 재사용하고, 비슷한 것들을 하나로 묶기(일반화) 위해 쓴다. 근데 비슷하다고 무조건 상속하면 안 되고, "A는 B다(is-a)", "A는 B의 한 종류다(is-a-kind-of)"가 말이 될 때만 해야 한다.

강아지, 뱀, 독수리는 동물이니까 동물을 상속해도 된다. 반면에 고양이 다리가 4개고 책상 다리도 4개라고 고양이가 책상을 상속하면 안 된다. 슬라이드에 "Nop!"이라고 크게 써 있었다.

그리고 자식은 부모의 모든 걸 물려받는 게 아니라, 부모가 허락한 멤버만 물려받는다. 물려받은 걸 오버라이딩하거나 새 기능을 붙여서 확장한다.

### extends와 implements

```java
public class Student extends Person implements 공부기능 { ... }
public class StudentWorker extends Student implements 공부기능, 일하기기능 { ... }
```

`extends`는 클래스를 상속할 때 쓴다. "Student는 Person이다"라서 의미도 맞다. `implements`는 인터페이스를 구현할 때 쓰는데, 이 클래스를 어떻게 쓰는지(기능)를 알려주고 실제 구현은 클래스한테 맡기는 거다.

꼭 기억할 것. 클래스는 하나만 상속할 수 있고, 그 대신 기능을 따로 떼서 인터페이스로 만들었다.

```java
public class 로봇강아지 extends 로봇, 강아지 { }                   // 안 됨. 다중 상속 불가
public class 로봇강아지 extends 강아지 implements 청소기능, 충전기능 { } // 됨
public class 로봇강아지 extends 로봇 implements 강아지기능 { }         // 이것도 됨
```

로봇강아지를 강아지로 볼지 로봇으로 볼지는 정답이 없다. 요구사항에 맞게 정하면 된다.

### 상속의 장점과 단점

장점은 이렇다.
- 같은 멤버를 여러 번 안 써도 돼서 클래스가 간단해진다
- 클래스를 계층으로 나눌 수 있고, 부모 타입으로 참조할 수 있다
- 재사용이랑 확장이 쉬워서 빨리 만들 수 있다

근데 단점도 크다.
- 결합이 강하다. 자식이 부모 구현에 기대고 있어서 부모를 고치면 자식 전부가 영향을 받는다. 그래서 테스트도 엄청 많이 해야 한다.
- 캡슐화가 약해진다. 자식이 부모 내부에 접근할 수 있고, 새 자식을 만들려면 부모 구현을 다 알아야 한다.
- 남발하면 클래스가 필요 이상으로 많아진다.
- 상속 단계가 깊어질수록 코드를 이해하고 고치기 어려워진다.

그래서 요즘은 클래스 상속보다 인터페이스나 합성 구조를 쓰라고 한다. 자프실2에서는 연관, 합성, 의존 관계를 써서 상속 문제를 피하는 방법을 배우고, 나중에 SOLID 원칙(OCP, LSP, DIP)이나 디자인 패턴이랑 연결된다.

그렇다고 "그럼 상속 몰라도 되나요?"는 아니다. 상속을 알아야 피해 가는 방법도 이해할 수 있다.

## 인터페이스

인터페이스는 원래 메소드만 정의해두는 특별한 클래스였다. 기능을 적어두는 용도.

그런데 개발자들이 "이거 너무 귀찮으니까 좀 추가해주세요" 하는 목소리가 반영돼서, Java 8부터는 인터페이스 안에 구현까지 된 메소드(default 메소드)를 넣을 수 있게 됐다. 인터페이스에서 구현해뒀으면 그냥 가져다 써도 되고 오버라이딩해도 된다.

- 인터페이스끼리도 상속할 수 있고, 인터페이스는 여러 개를 상속할 수 있다.
- 변수는 못 넣고 상수만 넣을 수 있다. `public static final`을 생략해도 상수라서 일반 변수로 착각하면 안 된다.

| 버전 | 인터페이스에 넣을 수 있는 것 |
| --- | --- |
| Java 7까지 | 상수, 추상 메소드 |
| Java 8 | default 메소드, static 메소드 추가 |
| Java 9 | private 메소드 추가 |
| 지금도 안 되는 것 | 일반 필드(멤버 변수) |

### 인터페이스로 접근하면 안전한 이유

클래스로 직접 접근하기보다 인터페이스로 접근하는 걸 권한다고 하셨다. 비유가 재밌었는데, 우리는 속성이 100개, 기능이 5000개쯤 되는 사람이지만 학교에 오면 교수님께서는 우리를 "학생 기능"으로만 본다고. 필요한 기능만 보이게 접근하니까 안전하다.

## 다형성: 같은 이름, 다른 동작

`소리내기1()`, `소리내기2()`처럼 이름을 따로 만들지 않고, 같은 이름으로 객체마다 다르게 동작하게 하는 게 다형성이다. OOP에서 제일 중요한 개념 중 하나다.

다형성은 오버로딩과 오버라이딩으로 나뉜다.

- 오버로딩: 같은 클래스 안에서 이름은 같고 파라미터(개수, 타입, 순서)만 다른 메소드를 여러 개 만드는 것. `println(int)`, `println(String)`처럼. 리턴 타입은 구분 기준에 안 들어간다. 어떤 메소드가 불릴지 컴파일할 때 정해진다(정적 바인딩).
- 오버라이딩: 상속받은 메소드를 자식이 다시 정의하는 것. 동물은 소리를 내는데 강아지는 멍멍, 고양이는 야옹. 어떤 메소드가 실행될지 실행 중에 정해진다(동적 바인딩).

### 동적 바인딩

```java
Animal ani = new Cat();   // 업캐스팅
ani.play();               // Cat에서 오버라이딩한 play()가 실행된다

Animal[] 동물농장 = { new Cat(), new 강아지(), new 오리() };
for (Animal a : 동물농장) a.play();   // 각자 자기 play()
```

`ani.play()`를 쓸 때 실제로 어느 `play()`가 실행될지는 컴파일할 때는 모르고 실행해봐야 안다. 자식 클래스부터 찾아보고, 없으면 부모 쪽으로 올라가면서 찾는다.

## 클래스, 객체, 그리고 관계

클래스는 설계도나 붕어빵 틀이고, 객체는 그 틀로 찍어낸 붕어빵이다. 실제 메모리를 차지하는 실체라서 인스턴스라고도 부른다. `new`는 C에서 `malloc()` 쓰던 걸 떠올리면 된다.

### 관계는 이 세 가지만 기억하기

- is-a (상속): "사람은 동물이다"
- has-a (집합): "자동차는 엔진, 타이어, 핸들로 이루어져 있다"
- use-a (사용): "사람이 자동차를 운전한다"

그리고 is-a를 빼면 나머지는 전부 연관(association)이나 의존(dependency)으로 볼 수 있다고 하셨다.

주의할 점이 하나 있었다. 엔진, 타이어가 각각 객체일 때 집합 관계라고 하는 거고, `String 엔진`, `int 타이어`처럼 그냥 값이면 필드라고 부르지 관계라고 하지 않는다.

연관이냐 의존이냐는 어떻게 쓰느냐로 나뉜다.
- 필드로 계속 갖고 있으면서 쓰면 association. 내가 핸드폰으로 전화를 거는 것처럼 (핸드폰을 갖고 있음)
- 메소드 파라미터로 잠깐 받아서 쓰면 dependency. 짱구가 택시를 타는 것처럼 (택시를 갖고 있지 않음)

### 클래스 다이어그램 그릴 때

- 위로 올라가는 선(상속, 인터페이스 구현)은 계층을 나타내고, 나머지 선은 관계를 나타낸다.
- 누가 누구를 쓰는지 파악했으면 쓰는 쪽에서 화살표를 긋는다.
- 양쪽으로 화살표를 긋는 건 가능하면 피한다. A도 B를 쓰고 B도 A를 쓰면 서로 물고 물려서 꼬인다. 한 방향만 쓰자.
- 다이아몬드 모양은 툴마다 다르니까, 헷갈리면 그냥 화살표 위에 `<<관계>>`라고 적어도 된다.

## 필기에서 잘못 적었던 것

수업 들으면서 급하게 적은 필기를 슬라이드랑 녹음으로 다시 확인해보니까 잘못 적은 게 세 개 있었다.

- "인터페이스는 정수X 상수만 가능"이라고 적었는데, 정수가 아니라 **변수**가 안 되는 거였다.
- "default는 내부/상속 public, 외부 private"이라고 적었는데, default는 **같은 패키지 안에서만** 열린다. 다른 패키지에 있으면 상속받은 자식도 못 쓴다. 다른 패키지라도 상속 관계면 열리는 건 protected다.
- "업캐스팅은 인터페이스는 불가"라고 적었는데, 인터페이스는 **new로 만드는 게** 안 되는 거고, 인터페이스 타입으로 참조하는(업캐스팅하는) 건 된다.

## 정리

- 캡슐화: 클래스로 감싸고, 기본은 private, 필요하면 getter/setter
- 상속: is-a일 때만. 클래스는 하나만 상속하고 나머지는 인터페이스로. 단점이 커서 요즘은 되도록 피한다
- 다형성: 오버로딩은 컴파일할 때, 오버라이딩은 실행할 때 정해진다
- 관계: is-a, has-a, use-a. is-a가 아니면 연관 아니면 의존
