이번 주까지가 복습이다. 짱구네 집 퀴즈는 내가 이걸 제대로 아는지 스스로 확인해보는 용도라고 하셨다. 교수님이 20분 정도 주셨는데, 그보다 훨씬 오래 걸리면 자프실1 내용을 다시 봐야 한다는 신호라고.

## 제일 먼저 기억할 것

> 호출은 부모 타입으로, 실행은 자식 타입의 메소드로

업캐스팅한 부모 타입 이름으로 메소드를 부르면, 실제로는 메모리에 있는 객체 중 제일 아래 자식이 오버라이딩한 메소드가 실행된다.

## 상속 관계

```text
할머니            요리하기()  → 된장, 고추장, 김치 담그기
  └ 엄마          요리하기()  → 에어프라이어 고구마, 스파게티   (오버라이딩)
                  청소하기()  → 구석구석 깨끗이 닦기           (추가)
      └ 짱구      요리하기()  → 전자레인지로 컵라면             (오버라이딩)
                  청소하기()  → 이불 덮기                      (오버라이딩)
```

교수님이 여기에 함정을 하나 넣어두셨다고 했다. 이름을 할머니, 엄마, 짱구로 해놓으니까 "엄마 타입으로 부르면 엄마 요리가 나오겠지" 하고 헷갈린다는 것.

짱구의 청소하기가 웃겼다. 청소하라고 하면 물건을 전부 침대 위에 올려놓고 이불 덮고 깨끗하다고 한다. 이렇게 오버라이딩으로 기능을 넓힐 수도 있고 오히려 줄일 수도 있다. 다만 아예 지울 수는 없다.

### 짱구를 만드는데 왜 할머니 생성자부터 실행될까

생성자 공부하다가 이 질문이 들어왔다고 한다. 답은 상속이라서다. 짱구를 만들려면 이미 있는 할머니, 엄마를 바탕으로 만들어야 하니까.

얼굴을 그린다고 치면 동그라미를 먼저 그리고 그 위에 눈, 코, 입을 그리는 것과 같다. 입만 덩그러니 그려놓고 사람 얼굴이라고 할 수는 없다.

## Quiz #1: mom.요리하기()로 만들 수 있는 요리는?

```java
짱구 s = new 짱구();
엄마 mom = new 짱구();   // 업캐스팅
mom.요리하기();
```

보기는 1) 된장과 고추장 2) 스파게티 3) 컵라면 4) 전부 5) 없다(에러)였다.

정답은 3번 컵라면이다.

엄마 타입 `mom`으로 불렀으니까 스파게티일 것 같은데, 메모리에 실제로 만들어진 건 `new 짱구()`, 즉 짱구다. `mom`은 짱구를 엄마의 설계도로 바라보고 있는 것뿐이다. 엄마 설계도에 `요리하기()`, `청소하기()`가 있으니까 이름은 보이는데, 실제로 실행되는 건 짱구가 "난 내 방식대로 할래" 하고 오버라이딩한 요리하기다. 그래서 컵라면.

### 할머니 타입으로 부르면 청소하기가 보일까

```java
할머니 g = new 짱구();
g.요리하기();   // 컵라면
g.청소하기();   // 컴파일 에러
```

안 보인다. 할머니 설계도에는 `요리하기()`밖에 없으니까. 할머니가 우리한테 "공부 좀 해라, 학원 가라" 같은 잔소리는 안 하시는 것처럼.

## Quiz #2: a, b, c로는 어떤 요리를 할 수 있을까

```java
할머니 a = new 짱구();
엄마   b = new 짱구();
짱구   c = new 짱구();
```

- `a`(할머니 타입): 요리하기만 보이고, 부르면 컵라면. 청소하기는 안 보인다.
- `b`(엄마 타입): 요리하기, 청소하기가 보이고, 요리하기는 컵라면, 청소하기는 이불 덮기.
- `c`(짱구 타입): 짱구가 가진 게 다 보이고 결과는 b랑 같다.

셋 다 컵라면이다. 실제로 만든 게 전부 짱구니까.

### 그럼 짱구는 스파게티나 된장은 절대 못 만들까

만들 수 있다. 방법이 몇 가지 있다.

```java
public class 짱구 extends 엄마 {

    // 방법 1: 엄마처럼 요리하기. 짱구 입장에서 super는 엄마
    public void 엄마처럼요리하기() {
        super.요리하기();                 // 스파게티
    }

    // 방법 2: 할머니처럼 요리하기
    public void 할머니처럼요리하기() {
        // super.super.요리하기();       // 안 된다. super는 한 단계만 올라간다
        super.할머니처럼요리하기();        // 엄마한테 이 메소드가 있다는 전제에서 가능
    }

    // 방법 3: 요리하기를 오버로딩해서 파라미터로 받은 사람한테 부탁하기
    public void 요리하기(엄마 m) {
        m.요리하기();
    }
    public void 요리하기(할머니 g) {
        g.요리하기();                     // 진짜 할머니 객체를 넘기면 된장, 고추장
    }
}
```

`super`는 바로 위 한 단계까지만 간다. `super.super`는 안 된다. 그래서 방법 2를 쓰려면 엄마 클래스에 `할머니처럼요리하기()`가 따로 있어야 한다.

방법 3은 "엄마한테 해달라고 해야지, 할머니한테 부탁해야지" 하는 느낌이다. 짱구가 엄마를 이용해서 요리하는 것.

## Quiz #3: 어떤 타입으로 보느냐에 따라 보이는 멤버가 다르다

설계도를 조금 더 늘렸다.

| 클래스 | 속성 | 메소드 |
| --- | --- | --- |
| 할머니 | `+지팡이`, `-빨간내복`, `#레시피` | 요리하기() |
| 엄마 | `-일기장`, `+핸드폰압수bag` | 요리하기(), 청소하기(), 할머니처럼요리하기(), 핸드폰뺏기(짱구 s) |
| 짱구 | `-핸드폰` | getPhone(), setPhone(), 요리하기(), 청소하기(), 요리하기(엄마 m), 요리하기(할머니 g), 엄마처럼요리하기(), 할머니처럼요리하기(), 열심히공부하기(), 공부하기() |

클래스 다이어그램에서 위 칸은 속성(필드), 아래 칸은 메소드고, 둘을 합쳐서 멤버라고 부른다. `+`는 public, `-`는 private, `#`은 protected다. 할머니의 빨간 내복은 누구한테도 안 보여주지만 레시피는 자식들한테 물려줄 수 있다.

엄마한테 핸드폰 압수 bag이 있는 이유는, 짱구가 공부하는 척하면서 핸드폰을 하니까 뺏어서 넣어두려고.

### 1. 엄마 mom = new 엄마(); 일 때 mom.으로 볼 수 있는 것

private은 아무리 자기 거라도 바깥(Main)에서는 안 보인다. 그 클래스 안에서만 보인다. 그래서 엄마의 일기장, 할머니의 빨간 내복은 안 보인다.

- 할머니한테 물려받은 것: 지팡이, 레시피, 요리하기() (요리하기는 엄마가 오버라이딩했다)
- 엄마한테 있는 것: 핸드폰압수bag, 요리하기(), 청소하기(), 할머니처럼요리하기(), 핸드폰뺏기()

레시피는 protected라서 Main이 같은 패키지에 있을 때 보인다.

### 2. 짱구 s = new 짱구(); 일 때 s.으로 볼 수 있는 것

위에서부터 다 찾아봐야 한다. 할머니한테 받은 것, 엄마한테 받은 것, 짱구가 열어둔 것까지.

- 속성: 지팡이, 레시피, 핸드폰압수bag. 짱구의 핸드폰은 private이라 안 보인다.
- 메소드: 짱구 클래스에 있는 public 메소드 전부랑 엄마한테 받은 핸드폰뺏기()
- 요리하기(), 청소하기(), 할머니처럼요리하기()는 짱구가 오버라이딩한 것

### 3. 엄마 mom = new 짱구(); 일 때 mom.으로 볼 수 있는 것

이게 제일 중요했다. 짱구를 만들었어도 엄마 타입으로 접근했으니까 엄마 설계도 기준으로 본다.

- 속성: 지팡이, 레시피, 핸드폰압수bag
- 메소드: 요리하기(), 청소하기(), 할머니처럼요리하기(), 핸드폰뺏기()
- 짱구가 새로 추가한 열심히공부하기(), 요리하기(엄마 m) 같은 건 안 보인다.
- 대신 보이는 메소드 중에 짱구가 오버라이딩한 건 짱구 버전으로 실행된다.

## Quiz #4: 짱구가 엄마한테서 핸드폰 되찾기

짱구는 핸드폰이 없으면 열심히 공부하고, 핸드폰이 있으면 공부하는 척만 한다. 엄마가 핸드폰을 뺏어가면 열심히 공부하는데, 중간에 짱구가 엄마 bag에서 몰래 다시 가져오고 싶어한다. 엄마의 `핸드폰뺏기()`랑 비슷하게 만들면 된다.

```java
public class 짱구 extends 엄마 {
    private 핸드폰 phone;

    public 핸드폰 getPhone() { return phone; }
    public void setPhone(핸드폰 h) { this.phone = h; }

    public void 공부하기() {
        if (phone == null) System.out.println("열심히 공부합니다. 열심열심!");
        else System.out.println("공부하는 척합니다...");
    }

    // 엄마를 파라미터로 받아서 엄마 bag에서 가져온다
    public void 핸드폰뺏기(엄마 m) {
        if (m.get핸드폰압수bag() == null) {
            System.out.println("엄마 bag이 비었어요.");
            return;
        }
        System.out.println("몰래 가져왔습니다.");
        this.setPhone(m.get핸드폰압수bag());   // 1. 내 폰으로 넣고
        m.set핸드폰압수bag(null);              // 2. 엄마 bag은 비운다
    }
}
```

핸드폰을 가져오려면 핸드폰이 어디 있는지 알아야 하고 누구 걸 가져올지 알아야 한다. 그렇게 생각하면 파라미터가 `엄마 m`이라는 게 나온다.

마지막 줄에서 엄마 bag을 `null`로 만드는 게 진짜 중요하다고 하셨다. 안 그러면 엄마도 핸드폰을 갖고 있고 짱구도 갖고 있는 이상한 상황이 된다.

`null`을 필드에 바로 넣어도 되긴 하는데 setter/getter로 하는 게 훨씬 깔끔하다. 핸드폰 클래스는 내용 없이 빈 클래스로 만들어둬도 된다.

`this`는 여기서는 붙여도 된다. static 메소드에서는 `this`를 못 쓰니까 자동 생성 코드에서는 상황에 따라 안 붙는 것뿐이다. 그리고 교수님이 늘 하시는 말씀. 이 코드만 정답이 아니고 방법은 여러 가지다.

## 상속은 좋기만 할까

꼭 확인해보라고 하신 질문들이다.

- 상속은 왜 쓸까? 인터페이스는 왜 쓸까?
- 상속에 장점만 있을까? 사실 단점이 더 많다. 결합이 너무 강하다.
- 그래서 실무에서는 상속을 피하고 합성이나 연관 관계를 쓴다.
- 이게 SOLID의 OCP, LSP, DIP나 여러 디자인 패턴이랑 이어진다.

그렇다고 상속을 몰라도 되는 게 아니라, 상속을 알아야 피해 가는 방법도 찾아볼 수 있다. 피해 가는 방법까지 조사해보면 완벽하다고 하셨다.

## 정리

- 호출은 부모 타입으로 하지만, 실행은 제일 아래 자식이 오버라이딩한 메소드로 된다
- 무엇이 보이는지는 참조 타입(어떤 설계도로 보느냐)이 정하고, 무엇이 실행되는지는 실제 객체가 정한다
- private은 자기 클래스 밖에서는 안 보인다. protected는 상속 전용인데 같은 패키지에서도 보인다
- `super`는 한 단계만 올라간다. 더 위의 동작이 필요하면 메소드를 따로 만들거나 파라미터로 받아서 부탁한다
- 객체를 옮길 때는 원래 있던 자리를 비우는 것까지 해야 끝이다
